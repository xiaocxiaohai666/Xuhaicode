## 一、线程池核心：政府大厅类比

主线程 = 大厅总接待台，单线程同一时刻只能处理一件事。
开多个工作线程 = 开设多个业务窗口，并行处理任务。
**窗口（线程）数量固定，不能无限新建销毁线程**：频繁创建销毁线程开销很大。
任务队列 = 取号排队区。大量请求涌过来，不直接拒绝，任务封装好丢进队列缓冲（削峰），空闲窗口从队列取任务执行。

### 1. 任务队列是共享临界资源，必须加锁+条件变量

- 生产者（主线程epoll收到事件）往队列投放任务；消费者（工作线程）从队列取出任务。
- 生产、消费不能同时修改队列，会出现数据错乱、同一个任务被两个线程抢到。
- `pthread_mutex_t`保护队列读写；`pthread_cond_t`处理：队列为空，工作线程阻塞休眠；来了新任务唤醒休眠线程。
- `pthread_cond_wait`：进入条件变量等待队列，睡觉前自动释放锁；被唤醒后重新竞争锁；**必须while循环判断条件，防御虚假唤醒**。

> 注意：线程池队列只存**任务**，不存数据库连接；数据库连接池是另一套资源管理，二者可以共用同一套线程池工作线程。

**【对应代码】生产者往队列投任务（加锁 + 唤醒）** [service.cpp#L305-L320](file:///home/xiaoc/mycode/csproject/service.cpp#L305-L320)

```cpp
void Thread_Pool::add_Task(Socket *csocket) {
  pthread_mutex_lock(&mutex);           // 加锁保护队列
  if (task_Num >= dequeue_size) {
    delete csocket;
    cout << "dequeue_size is full!add_Task false!" << endl;
    pthread_mutex_unlock(&mutex);
    return;
  }

  dequeue[rear].task = csocket;         // 任务入队
  rear = (rear + 1) % dequeue_size;
  task_Num++;

  pthread_cond_signal(&cond);           // 唤醒一个休眠的工作线程
  pthread_mutex_unlock(&mutex);         // 释放锁
}
```

**【对应代码】消费者从队列取任务（while循环判断 + cond_wait）** [service.cpp#L334-L362](file:///home/xiaoc/mycode/csproject/service.cpp#L334-L362)

```cpp
void Thread_Pool::Work() {
  while (true) {
    pthread_mutex_lock(&mutex);

    while (task_Num == 0 && status == true) {
      pthread_cond_wait(&cond, &mutex);
      //这是条件休眠，进入到条件变量的休眠队列，进入条件变量的休眠队列是会自动释放锁，这与sleep是不相同的。
    } // 不能用if，要用while，以防虚假唤醒。

    if (status == false) {
      cout << "ThreadPool not run....." << endl;
      break;
    }

    Socket *tmp = dequeue[front].task;   // 取出任务
    front = (front + 1) % dequeue_size;
    task_Num--;
    pthread_mutex_unlock(&mutex);        // 取完任务立刻释放锁，再执行业务

    tmp->Do_client();
  }
  pthread_mutex_unlock(&mutex);
}
```

### 2. 线程入口函数参数为什么传整个线程池对象指针，而不是仅仅传任务队列指针

- 如果只传队列指针：只能操作队列，线程池里面其他成员（最大线程数、线程数组、开关标记等）访问不到。
- 传入整个类的this指针，线程函数拿到完整对象，内部可以访问全部成员变量、调用成员方法。

> C++注意：pthread_create是C接口，只能接收`void*`类型参数，不能直接传成员函数，一般封装静态函数作为线程入口，把对象指针作为参数传入。

## 二、epoll + EPOLLONESHOT 知识点

### 1. EPOLLONESHOT 标志位作用

> 不是把fd从epoll集合删除，只是**触发一次事件后就静默，不再上报该fd任何事件**，fd仍然保存在epoll内。

业务场景：**多线程+epoll模型**
- epoll_wait主线程拿到socket就绪事件，把socket交给线程池子线程做读写业务；
- 设置ONESHOT，保证：在子线程处理期间，主线程epoll‑wait**不会再次收到这个socket的事件通知**，避免同一个socket同时丢给2个线程处理，防止多线程争抢同一个socket造成数据错乱。
- ⚠业务处理完毕后，必须调用`epoll_ctl(EPOLL_CTL_MOD)`重新设置EPOLLIN | EPOLLONESHOT，重新激活监听，才能继续接收该客户端后续报文。

**【对应代码】新连接加入epoll时设置 ONESHOT** [service.cpp#L125-L130](file:///home/xiaoc/mycode/csproject/service.cpp#L125-L130)

```cpp
ev_client_accpet.data.ptr = recvSock;

if (epoll_ctl(epfd, EPOLL_CTL_ADD, conn_fd, &ev_client_accpet) == -1) {
```

**【对应代码】业务处理完毕后 MOD 重新激活监听** [service.cpp#L246-L254](file:///home/xiaoc/mycode/csproject/service.cpp#L246-L254)

### 2. epoll事件联合体`data.ptr`存放类对象地址

epoll_event的`data`有两种选择：`fd`存文件描述符；`ptr`存**自定义结构体/类对象堆地址**。
- 把客户端连接管理结构体（包含fd、缓冲区、状态）在堆上new出来，把对象指针赋值给`ev.data.ptr`。
- epoll事件触发，通过ptr直接拿到整个连接对象，不用自己维护fd和对象的映射表。
- 内存设计思路：复用堆上的连接对象，连接关闭后不要立刻释放，或者统一管理，避免频繁new/delete带来大量堆碎片、内存开销。

### 3. listen_fd监听套接字：阻塞 vs O_NONBLOCK（高频考点）

listen_fd的属性决定`accept()`行为，和epoll是LT水平触发还是ET无关。

1. 默认listen_fd是**阻塞**：
    - 监听队列为空，`accept()`直接阻塞卡住当前线程。
    - 重大风险：如果accept交给线程池的工作线程执行，监听队列为空时，工作线程直接卡死在accept，窗口被占死，线程池可用线程变少。
2. 设置`fcntl(listen_fd, F_SETFL, O_NONBLOCK)`变为非阻塞：
    - 监听队列为空，`accept()`立刻返回‑1，`errno == EAGAIN / EWOULDBLOCK`，代表没有新连接，函数立刻返回，不会阻塞线程。

> 工程标准写法：**listen_fd一律设置非阻塞**，配合epoll LT模式，在主线程执行accept，不要把accept丢进工作线程。

**【对应代码】listen_fd 设置非阻塞** [service.cpp#L724-L728](file:///home/xiaoc/mycode/csproject/service.cpp#L724-L728)

```cpp
// listen socket 设为非阻塞,accept 队列空时返回 EAGAIN 而不是阻塞
int flags = fcntl(lis_fd, F_GETFL, 0);
fcntl(lis_fd, F_SETFL, flags | O_NONBLOCK);
// 因为是lis_fd为空导致的阻塞，所以我们这个将模式设为非阻塞
```

**【对应代码】accept 返回 -1 时判断 EAGAIN 优雅退出** [service.cpp#L106-L119](file:///home/xiaoc/mycode/csproject/service.cpp#L106-L119)

```cpp
int conn_fd = accept(fd, (struct sockaddr *)&client_addr, &client_addr_len);

if (conn_fd < 0) {
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        // listen 队列空了,别的 worker 已经把连接取走了,正常退出
        delete this;
        return;
    }
    perror("accept failed");
    cout << "accept failed! errno=" << errno << endl;
    delete this;
    return;
}
```

> **项目踩坑记录**：最初 listen_fd 用 LT 模式且未设非阻塞，accept 丢进线程池工作线程执行。主线程疯狂生成 accept 任务，5 个 worker 线程全部卡死在 accept()（监听队列已空），线程池瘫痪。修复方案：listen_fd 设 O_NONBLOCK + accept 判 EAGAIN 退出。

### 4. 文件描述符fd从3开始的原因

每个进程启动，操作系统自动分配3个文件描述符：
- fd=0：标准输入 stdin
- fd=1：标准输出 stdout
- fd=2：标准错误 stderr
后面socket、open打开文件，操作系统分配当前进程**最小可用数字**，所以第一个socket fd就是3。

> ⚠注意：fd=3是**当前进程内编号**，不是全局编号！不同进程socket fd都可以是3，互不干扰，不能拿fd值区分不同客户端。

（本条为系统知识点，项目代码中 client 连接后打印的 conn_fd=3 即为此现象的体现，无专门代码段。）

### 5. 短时间大量触发EPOLLIN，连续生成大量任务，但是accept拿不到连接

epoll_wait速度远快于accept处理速度：内核监听队列还有连接，epoll反复上报EPOLLIN事件，主线程疯狂封装任务丢进队列；当内核监听队列已经被accept取空之后，后续任务再调用accept就会出问题。

> 解决方案：listen_fd设置非阻塞，accept循环尽可能把内核队列所有连接全部取干净；不要把accept业务交给线程池子线程。

**【对应代码】listen_fd 用 LT 模式 + 非阻塞（避免主线程空转生成无效任务）** [service.cpp#L765-L767](file:///home/xiaoc/mycode/csproject/service.cpp#L765-L767)

```cpp
struct epoll_event ev_listen;
ev_listen.events = EPOLLIN;          // listen fd 用 LT 水平触发
ev_listen.data.fd = lis_fd;
```

> **项目踩坑记录**：曾尝试把 listen_fd 改成 ET 边沿触发，但最终回退到 LT + 非阻塞方案。LT 模式下只要监听队列有连接就会持续上报 EPOLLIN，配合非阻塞 accept 判 EAGAIN，工作线程不会卡死。ET 模式虽然只通知一次，但需要 accept 循环取干净，实现更复杂，本项目选择 LT 更稳妥。

## 三、数据库：短连接、长连接、数据库连接池对比

### 1. 短连接方案（项目当前方案）

每次客户端请求业务：`mysql_real_connect`建立连接 → SQL操作 → `mysql_close`关闭。

### 2. 数据库长连接（不使用连接池）

一个客户端TCP长连接，永久绑定一条MySQL连接。
- 致命缺陷：成千上万客户端TCP挂在服务器，就算客户端不发任何请求，也持续占用MySQL连接资源，很容易打满`max_connections`上限，MySQL拒绝新连接。

> 项目未采用此方案，无对应代码段。曾考虑把 Mysql_Client 作为 RecvSocket 的成员变量（长连接），但会导致每个客户端独占一个MySQL连接，并发上去必崩。

---

### 3. 数据库连接池方案（优化方案）

程序启动，预先创建固定N条MySQL连接，保存到数组，搭配状态标记：空闲 / 占用；搭配互斥锁+条件变量。
- `get_conn()`：工作线程向池子借出一条空闲MYSQL*；无空闲连接，线程cond_wait阻塞等待别人归还。
- `release_conn()`：业务结束**不执行mysql_close**，归还连接标记为空闲，留给后续任务复用。

> ⚠归还前必须处理事务：如果业务异常，要手动rollback，不能把残留未提交事务的连接还给池子，会污染下一次业务。
- 业务任务依然丢进**服务器原有线程池的任务队列**，数据库连接池只管理MYSQL*资源，不管理业务任务。

> 项目尚未实现连接池，为后续优化方向，无对应代码段。事务处理部分可参考现有 Db_Yd_Ticket / Db_Cancel_Ticket 中的 Begin/RollBack/Commit 写法。

## 四、模块职责划分（背诵总结）

1. **epoll**：只负责监听socket文件描述符IO事件；
2. **线程池**：管理工作线程、任务队列，消费epoll产生的业务任务；
3. **数据库连接池**：只管理MYSQL*数据库连接资源的借出归还；

> 三个模块各司其职，数据库连接池不要自己再做任务队列，任务排队交给线程池。

## 六、其他项目踩坑记录（补充）

### 1. 客户端关闭后服务端死循环打印"Json 解析失败"

**原因**：`recv()` 返回 0 表示对端正常关闭，但原代码只判断了 `recv_num < 0`，`==0` 走进 else 分支，buff 为空导致 JSON 解析失败，解析失败后又重新 MOD EPOLL，死循环。

**修复**：单独处理 `recv_num == 0`，设置 `tag=true` 直接关闭连接。
- → 对应 [service.cpp#L166-L172](file:///home/xiaoc/mycode/csproject/service.cpp#L166-L172)

### 2. 连接关闭时未从 epoll 删除 fd（幽灵事件风险）

**原因**：原来 `delete this` 只触发析构 `close(fd)`，依赖内核自动移除 epoll，未显式 DEL。

**修复**：`delete this` 之前先 `epoll_ctl(EPOLL_CTL_DEL, fd, NULL)`，顺序必须是 **先 DEL 后 close**，否则 fd 复用会误删新连接。
- → 对应 [service.cpp#L246-L248](file:///home/xiaoc/mycode/csproject/service.cpp#L246-L248)

### 3. SQL 拼接错误导致预约功能完全不可用
