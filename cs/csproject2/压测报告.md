# 票务预约系统压测报告（csproject2）

> 测试对象：`/home/xiaoc/mycode/cs/csproject2`
> 配置变更：工作线程数 5 → 10，MySQL 连接池连接数 5 → 10
> 测试日期：2026-10-04

## 一、测试目的

在将线程池工作线程数与 MySQL 连接池连接数由 5 调整为 10 之后，重新评估系统在并发压力下的：

1. 吞吐能力（QPS）与响应延迟；
2. 业务正确性（并发抢票是否超卖、数据是否一致）；
3. 连接池容量是否充足（是否出现 `MYSQL CLIENT BUSSY`）；
4. 稳定性（是否出现连接异常、请求丢失）。

## 二、配置变更

| 项目 | 变更点 | 变更内容 |
| --- | --- | --- |
| 线程池 | `service.h` `#define thread_num` | 5 → 10 |
| 连接池 | `Connect_Pool` 的 `MAX_USER` / `C_P_array` | 由 `thread_num` 驱动，随之为 10 |

连接池实现中 `MAX_USER = thread_num`、`C_P_array = new Mysql_cli[thread_num]()`，连接建立、借用、归还循环均以 `thread_num` 为准，因此连接池连接数自动变为 10。

> 同批变更：`csproject`、`csproject2view`、`cs++view` 的 `thread_num` 均改为 10；`project` 线程池构造参数 `m_pool(4,1024)` 及默认成员 `thread_num` 改为 10。`csproject` 与 `project` 无连接池结构。

### 系统架构（被测对象）

```
客户端 --TCP:8888--> epoll 事件循环 --任务队列--> 线程池(10 worker)
                                              |
                                     MySQL 连接池(10 连接) --> MySQL 8.0
```

- 通信：TCP 长连接 + JSON 单请求/单响应协议；
- 连接模型：`EPOLLIN | EPOLLONESHOT`，单连接同一时刻仅一个线程处理；
- 预约：事务包裹 + 原子 SQL `UPDATE ticket_table SET count=count+1 WHERE Tk_id=? AND count<tk_max`，以 `mysql_affected_rows` 判定是否抢到票。

### 并发预约正确性（超卖验证）

- 测试前置：将票 1 设为 `count=0, tk_max=25`；
- 50 个客户端同时抢同一张票（每人 1 次）；
- 结果：收到 **25 个成功、18 个售罄失败**；
- 数据库校验：`ticket_table.count = 25`，`yd_table` 新增预约记录数 = **25**。

三者（客户端成功数 / count 增量 / 预约记录数）完全一致，**未发生超卖，也未出现 count 增量丢失**，验证了原子 SQL + 事务方案在高并发下的正确性。

## 五、关键发现

1. **读操作吞吐良好**：登录、查票在 50 并发下 QPS 约 2567 / 2705，P95 均在 23 ms 以内；提升到 100 并发时仍保持 1803 / 2278 QPS，说明 10 个工作线程可有效并行处理读请求。
2. **写操作稳定**：注册 50 并发 200 个请求全部成功，无失败、无排队丢弃，QPS 约 1510。
3. **并发抢票无超卖**：原子 SQL 配合行锁，使并发下 `count` 递增与预约记录写入严格一致（25 = 25 = 25）。
4. **连接池容量充足**：50~100 并发量级下从未触发连接池耗尽，10 个连接的池化复用足够覆盖当前压力。
5. **热点写延迟偏高**：并发预约平均延迟 52 ms（100 并发时约 88 ms），明显高于读操作。原因是所有请求争抢同一行记录，InnoDB 行锁将写操作串行化，属预期现象；若为多票分别抢购，延迟会显著降低。
6. **高并发写突发下存在连接重置（已定位根因，暂未修复）**

   **现象**：在"高并发 + 写操作"突发场景中，压测端出现 `ConnectionResetError`，次数波动明显（读场景基本为 0；预约 50 并发 33 次、100 并发 89 次），但服务端日志中 `recv 出错`、`JSON 解析失败` 均为 0 —— 客户端被重置，服务端却"一切正常"。

   **定位证据**：翻全量服务端日志，发现任务队列溢出提示 `dequeue_size is full!add_Task false!` 出现 **135021 次**（日志总计 171402 行），说明故障点在任务队列，而非连接处理本身。

   **根因（因果链）**：
   1. 监听 fd 以**水平触发（LT）**注册且未使用 `EPOLLONESHOT`（`service.cpp` 中 `ev_listen.events = EPOLLIN`），而 `accept` 是包成 `AccSocket` 任务交给 worker 执行的；
   2. 由于 LT 会持续报告仍就绪的监听 fd，主线程每轮 `epoll_wait` 都会重复投递 `AccSocket` 任务，**生产者速度远高于消费者**；
   3. 写请求耗时长（事务 + 同行行锁，单请求 50~90 ms），10 个 worker 全被占用、来不及 accept，队列（上限 `d_size = 1024`）瞬间被 `AccSocket` 灌满；
   4. 队列满时 `Thread_Pool::add_Task` 的处理是直接 `delete csocket`；
   5. 若被删除的是 `RecvSocket`，其析构函数为 `close(fd)`；而此时客户端请求数据仍在 socket 内核接收缓冲区中未被读取，**TCP 规定带未读数据关闭会发送 RST 而非 FIN**，客户端随即抛出 `ConnectionResetError`。

   这也解释了为什么读场景几乎不重置（队列排空快）、写场景重置多（队列被灌满），以及服务端为何没有任何错误日志（连接在 `recv` 之前就被关闭了）。

   **改进方案（备选）**：
   - **最小修复**：将监听 fd 改为 `EPOLLIN | EPOLLONESHOT`，并在 `AccSocket::Do_client` 处理后重新挂载，使在途 `AccSocket` 任务最多 1 个，从源头消除队列被灌爆的可能；
   - **加固**：`add_Task` 在队列满时不再 `delete` 活跃的 `RecvSocket`（改为回 busy 响应后优雅关闭，或内联处理），避免任何情况下"带未读数据 close"；
   - **可选**：采用有界队列 + 背压机制，或将 `accept` 移回主线程直接执行。

   **暂未修复的原因**：该改动涉及核心事件循环，影响面大，需完整回归压测；当前版本功能正确性（并发抢票无超卖）已验证，故先将其记录为已知限制并给出明确方案。

## 六、与上一版（5 线程 / 5 连接）对比

- 读操作 QPS 保持在 2500+ 水平，与上版相当；
- 上版在 50 并发注册场景出现过任务队列溢出导致的失败；本次 10 线程下注册 200/200 全部成功，写场景的排队能力明显改善；
- 上版并发抢票的竞态问题已由原子 SQL 修复，本次复测再次确认数据一致；
- 当前主要短板为"高并发写突发下的连接重置"（根因同样是任务队列溢出，详见"关键发现 6"）与"单行热点写的锁竞争"。

## 七、结论

将线程数与连接池调整为 10 后，系统在 50~100 并发量级下：

- 读操作（登录/查票）性能良好，延迟低、成功率高；
- 写操作（注册/预约）功能正确，并发抢票无超卖、数据一致；
- 连接池容量满足该压力水平，未出现池满返回；
- 整体已达到学生个人项目在 50~100 并发量级下稳定运行的目标。

后续优化建议：① 修复高并发写场景的连接重置（监听 fd 改 `EPOLLONESHOT` + 重挂，并加固 `add_Task` 溢出处理，详见"关键发现 6"）；② 为连接池引入条件变量等待，避免请求在池满时直接返回 busy；③ 热点票可考虑排队/削峰策略。
