# 五种线程池抗压测试报告

- 本次测量日期：**2026-10-04**（`CacheThreadPool` 去管理线程重构后的复测；09-09 那一版数据已整体替换，对比见第四节末尾）
- 测试程序：[main/test.cpp](main/test.cpp)（4 场景自动化压测，单次完整运行 < 60s）
- 测试对象：[include/ThreadPool.hpp](include/ThreadPool.hpp)、[include/TaskQueue.hpp](include/TaskQueue.hpp)

| 项目 | 配置 |

## 二、测试场景与指标

| 场景 | 负载模型 | 核心指标 |
|---|---|---|
| LIGHT 轻量任务 | **100 万**个空任务（仅计时+原子计数），8 个生产者线程并发提交 | 吞吐 TPS、端到端延迟（avg/P50/P95/P99/Max）、任务丢失数 |
| CPU 密集任务 | **20 万**个任务，每个执行 3000 次 `sqrt` 计算（约 8~10μs），8 生产者 | 纯计算吞吐 TPS、并行加速比 |
| SCHED 定时精度 | 1 万个延时任务，延时随机 50~500ms（仅 ScheduledThreadPool） | 实际触发时刻与预期时刻误差分布、提前执行数 |
| BURST 突发流量 | 3 波 × 3 万任务，波间空闲 900ms，50ms 采样完成速率 | 扩缩容响应、波峰速率 |

> 端到端延迟 = 任务执行时刻 − 提交时刻，含排队等待 + 调度 + 执行时间。所有场景均校验 `完成数 == 提交数`。

## 三、测试结果

### 场景 1：轻量任务吞吐与延迟（100 万任务）

| 线程池 | 总耗时 | 吞吐 TPS | 平均延迟 | P50 | P95 | P99 | 最大延迟 | 丢失 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| **WorkStealingThreadPool** | **0.457s** | **2,187,830** | 131.0μs | 61μs | 469μs | 1,044μs | 9,199μs | **0** |
| FixedThreadPool | 1.072s | 932,533 | 113.4μs | 71μs | 331μs | 646μs | 10,454μs | **0** |
| CacheThreadPool | 1.341s | 745,535 | 185.0μs | 133μs | 479μs | 889μs | 11,563μs | **0** |
| ScheduledThreadPool（delay=0） | 1.842s | 543,026 | 281.5μs | 226μs | 641μs | 1,156μs | 13,490μs | **0** |
| SignalThreadPool | 2.765s | 361,638 | 513.5μs | 384μs | 1,363μs | 2,195μs | 15,378μs | **0** |

- 所有池 **100 万任务全部完成、零丢失**；队列满时提交端阻塞背压（`m_notFull.wait`）工作正常，无任务被拒绝。
- 所有池 `drain 时间 ≈ 0`：生产者提交完最后一个任务时队列已基本被消费空，说明消费能跟上提交。
- 值得注意：**Fixed 的平均延迟（113.4μs）反而是五者最低**，WorkStealing 赢在吞吐而非单笔延迟。

### 场景 2：CPU 密集任务吞吐（20 万任务 × 3000 次 sqrt）

| 线程池 | 总耗时 | 吞吐 TPS | 相对单线程加速比 |
|---|---:|---:|---:|
| **WorkStealingThreadPool** | **0.710s** | **281,866** | **9.3×** |
| FixedThreadPool | 2.602s | 76,874 | 2.5× |
| CacheThreadPool | 2.805s | 71,293 | 2.3× |
| ScheduledThreadPool | 2.978s | 67,158 | 2.2× |
| SignalThreadPool | 6.589s | 30,355 | 1.0×（基准） |

- 理论加速比上限为 8（8 核）。WorkStealing 达到 9.3×，**超过 8 属于超线性**——原因是基准 `SignalThreadPool` 虽是单线程，但每条任务都要过一把互斥锁，它本身就不是理想的"无锁单线程"基线，所以这个倍数偏高，报告里如实说明。
- 共享队列的 Fixed/Cache/Scheduled 只有 2.2~2.5×：它们每次 `Put`/`Take` 都要抢同一把 `m_mutex`，锁上的串行化把并行度吃掉了。

### 场景 3：定时任务调度精度（ScheduledThreadPool，1 万任务）

| 指标 | 数值 |
|---|---:|
| 总耗时 | 13.978s（受 200 容量队列背压 + 50~500ms 延时约束） |
| 平均误差 | 378.6μs |
| P50 误差 | **291μs** |
| P95 误差 | 899μs |
| P99 误差 | 2,367μs |
| 最大误差 | 7,123μs |
| 最小误差 | 1μs |
| **提前执行任务数** | **0 / 10000** |

- 定时语义完全正确：**没有任何任务提前执行**，中位延迟误差不到 0.3ms。
- 尾部误差 P99 2.4ms / Max 7.1ms，比上一版（10.6ms / 34.6ms）**收窄了一个量级**。原因见第四节第 5 条：入队/取任务改成 `notify_one` 不再整队惊群，且 Cache 池不再有一个核在 `yield()` 空转跟工作线程抢 CPU。

### 场景 4：突发流量与扩缩容（3 波 × 3 万，波间空闲 900ms）

| 时刻 | Cache 累计完成 | 该 50ms 速率 | 状态 | Fixed 累计完成 | 该 50ms 速率 | 状态 |
|---:|---:|---:|---|---:|---:|---|
| 50ms | 22,979 | 459,560/s | 第 1 波，**生产者直接补线程** | 28,878 | 577,560/s | 第 1 波，8 线程立即满速 |
| 100ms | **30,000** | 140,420/s | 第 1 波清空 | **30,000** | 22,440/s | 第 1 波清空 |
| 150~950ms | 30,000 | 0/s | 空闲，线程 60ms 超时**自行退出** | 30,000 | 0/s | 空闲，线程常驻 |
| 1000ms | 45,185 | 303,700/s | 第 2 波到达 | **60,000** | 517,880/s | 第 2 波，无需预热 |
| 1050ms | **60,000** | 296,300/s | 第 2 波清空 | 60,000 | 0/s | — |
| 1950ms | 74,326 | 286,520/s | 第 3 波到达 | **90,000** | 413,020/s | 第 3 波，开局即峰值 |
| 2000ms | **90,000** | 313,480/s | 第 3 波清空 | 90,000 | 0/s | — |

- **Cache 池扩缩容机制实测有效**：空闲 900ms（> 60ms 超时）后线程确实全部回收；新流量到达后由**生产者在 `AddTask()` 里直接补线程**，每一波都能在 **50~100ms** 内清空。上一版要等 sudo 管理线程轮询到才补，第 1 波 50ms 时只有 10.8 万/s，这次是 **45.9 万/s**。
- **Fixed** 线程常驻，波峰更高（第 3 波 41.3 万/s vs Cache 31.3 万/s），但两者总耗时几乎一样（Cache 2.902s / Fixed 2.863s，差 1.4%）。
- 结论：Cache 用「空闲时零开销」换来每波约 2~4 万任务的爬坡损耗，在这个量级下代价可以忽略。

## 四、结论与分析

1. **WorkStealingThreadPool 综合性能最强**：轻量任务 219 万 TPS、CPU 任务 28.2 万 TPS，均为五种池最高。根本原因是每个工作线程拥有**独立队列和独立锁**，`AddTask` 用原子计数轮询分发把竞争分散到 8 把锁上，工作线程消费自身队列几乎无锁竞争。
2. **FixedThreadPool 延迟最低**：平均 113.4μs、P50 71μs 都是五者最优，常驻线程对突发流量响应即时；适合负载稳定、对延迟敏感的场景。
3. **CacheThreadPool 弹性最好，且不再有空转代价**：实测空闲 60ms 线程自行退出、流量恢复时由生产者直接补线程，每波 50~100ms 清空；适合流量潮汐明显的场景。**上一版"sudo 管理线程忙轮询占用约 1 个核"的代价已随重构消除。**
4. **SignalThreadPool 语义正确但无并行度**：单线程串行执行，任务严格按提交顺序执行（本报告未直接测顺序，但架构上保证），TPS 约为最快池的 1/6（WorkStealing 219 万）到 1/1.5（Scheduled 54 万），排队延迟随队列深度线性增长（最大 15ms）；适合需要顺序执行、不能并发的任务。
5. **ScheduledThreadPool 定时功能正确，尾部误差明显收窄**：1 万任务零提前执行，P50 误差 291μs、P99 2.4ms（上一版 10.6ms）。两个改善来源：① `TaskQueue` 的 `notify_all` → `notify_one`，到期时不再整队惊群抢锁；② Cache 池去掉了 `yield()` 空转的管理线程，少了一个核在工作线程旁边抢 CPU。它**仍然保留 sudo 管理线程**，这是当前已知的主要不一致点（见第五节）。
6. **可靠性**：全部场景累计 619 万任务零丢失、零拒绝、零崩溃，队列满背压阻塞正确，池销毁均能正常 join 回收线程。

## 五、问题清单

### 已解决

| 问题 | 当时的现象 | 解决方式 |
|---|---|---|
| **【惊群】** | `Add()` 每次入队 `notify_all` 唤醒全部等待线程 | `TaskQueue.hpp` 生产/消费各改 `notify_one`，只有 `Stop()`（必须唤醒全部）保留 `notify_all` |
| **【参数失效】** | Fixed / Cache 的 `deque_size` 没传给队列，容量恒为 200 | 改为 `m_taskqueue(deque_size)` |
| **【CPU 空转】**（Cache 部分） | `CacheThreadPool::Sudo()` 队列空时 `yield()` 死循环，空闲吃满一个核 | **管理线程整个拆掉**：生产者触发扩容 + worker 空闲超时自清理进 `m_dead_threads` 回收站 |
| **【定时尾部误差】** | P99 10.6ms / Max 34.6ms | 上述两项修复的综合效果，P99 降到 2.4ms |

### 仍存在（按优先级）

1. **【机制不一致】** `CacheThreadPool` 已是回收站方案，**`ScheduledThreadPool` 仍是旧的 `Sudo()` 管理线程**——`yield()` 空转吃核的问题在它身上还在。而且 `ScheduledThreadPool::ForceStopThreadGroup()` 是**持着 `b_mutex` 直接 join**，与 Cache 新版「锁内快照、出锁后 join」相反，仍有死锁风险。建议把 Cache 的写法搬过去（`wait_until` 精确到点的特殊性需要单独处理，但回收/停止的骨架可以直接复用）。
2. **【头文件结构】** `WorkStealingThreadPool` 定义在 [ThreadPool.hpp](include/ThreadPool.hpp) 的 `#endif`（第 517 行）之后，脱离 include guard 保护。当前只被一个编译单元包含所以能编译，被多个文件包含时会有重定义风险，建议移入 `#endif` 之前。
3. **【日志噪音】** `TaskQueue.hpp` 里 9 处 `std::cout << "task deque status = false"`，正常停止流程也会打印（本次压测打印了 8 行），建议降级为调试日志或删除。
4. **【偷取延迟】** WorkStealing 空闲线程 `wait_for(50ms)` 才重新扫一遍，任务被分到其他线程队列时最坏要 50ms 后才偷到（本次压测持续有负载，未触发；低负载突发时可能出现）。可在 `AddTask` 后对目标队列做一次 notify 改善。

> 注：本次为单次运行、虚拟机环境的数据，绝对值会随机器负载波动；但五种池的相对差距（WorkStealing ≫ Fixed/Cache/Scheduled ≫ Signal）在多次观察中稳定。复现命令：`mkdir -p build && cd build && cmake .. && make && ./bin/test`。
