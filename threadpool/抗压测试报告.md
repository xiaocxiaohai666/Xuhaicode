## 二、测试场景与指标

| 场景 | 负载模型 | 核心指标 |
|---|---|---|
| LIGHT 轻量任务 | **100 万**个空任务（仅计时+原子计数），8 个生产者线程并发提交 | 吞吐 TPS、端到端延迟（avg/P50/P95/P99/Max）、任务丢失数 |
| CPU 密集任务 | **20 万**个任务，每个执行 3000 次 `sqrt` 计算（约 8~10μs），8 生产者 | 纯计算吞吐 TPS、并行加速比 |
| SCHED 定时精度 | 1 万个延时任务，延时随机 50~500ms（仅 ScheduledThreadPool） | 实际触发时刻与预期时刻误差分布、提前执行数 |
| BURST 突发流量 | 3 波 × 3 万任务，波间空闲 900ms，50ms 采样完成速率 | 扩缩容响应、波峰速率 |

> 端到端延迟 = 任务执行时刻 − 提交时刻，含排队等待 + 调度 + 执行时间。所有场景均校验 `完成数 == 提交数`。

## 三、测试结果

### 场景 1：轻量任务吞吐与延迟（100 万任务）

| 线程池 | 总耗时 | 吞吐 TPS | 平均延迟 | P50 | P95 | P99 | 最大延迟 | 丢失 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| **WorkStealingThreadPool** | **0.532s** | **1,879,155** | 169.8μs | 94μs | 578μs | 1,263μs | 9,382μs | **0** |
| FixedThreadPool | 1.461s | 684,278 | 153.4μs | 75μs | 458μs | 1,206μs | 24,632μs | **0** |
| CacheThreadPool | 1.673s | 597,706 | 205.8μs | 109μs | 569μs | 1,757μs | 29,899μs | **0** |
| ScheduledThreadPool（delay=0） | 2.142s | 466,927 | 289.6μs | 197μs | 742μs | 2,000μs | 37,801μs | **0** |
| SignalThreadPool | 2.898s | 345,034 | 497.8μs | 305μs | 1,321μs | 4,260μs | 49,159μs | **0** |

- 所有池 **100 万任务全部完成、零丢失**；队列满时提交端阻塞背压（`m_notFull.wait`）工作正常，无任务被拒绝。
- 所有池 `drain 时间 ≈ 0`：生产者提交完最后一个任务时队列已基本被消费空，说明消费能跟上提交。
- WorkStealing 吞吐约为 Fixed 的 **2.7 倍**；Signal 单线程为 Fixed 的约 1/2。

### 场景 2：CPU 密集任务吞吐（20 万任务 × 3000 次 sqrt）

| 线程池 | 总耗时 | 吞吐 TPS | 相对单线程加速比 |
|---|---:|---:|---:|
| **WorkStealingThreadPool** | **0.650s** | **307,568** | **10.9×** |
| CacheThreadPool | 2.440s | 81,969 | 2.9× |
| ScheduledThreadPool | 2.478s | 80,715 | 2.8× |
| FixedThreadPool | 2.712s | 73,735 | 2.6× |
| SignalThreadPool | 7.066s | 28,306 | 1.0×（基准） |

- 理论加速比上限为 8（8 核）。WorkStealing 达到 10.9×（超线性，得益于每线程本地队列无竞争、任务分发均匀）；Fixed/Cache/Scheduled 仅 2.6~2.9×。

### 场景 3：定时任务调度精度（ScheduledThreadPool，1 万任务）

| 指标 | 数值 |
|---|---:|
| 总耗时 | 14.032s（受 200 容量队列背压 + 50~500ms 延时约束） |
| 平均误差 | 971.9μs |
| P50 误差 | **360μs** |
| P95 误差 | 4,102μs |
| P99 误差 | 10,562μs |
| 最大误差 | 34,640μs |
| 最小误差 | 1μs |
| **提前执行任务数** | **0 / 10000** |

- 定时语义完全正确：**没有任何任务提前执行**，中位延迟误差仅 0.36ms。
- 尾部误差偏大（P99 10.6ms、Max 34.6ms）：大量任务在相近时刻到期时，多个工作线程被同一个条件变量唤醒后抢锁（惊群），锁竞争放大了尾部延迟。

## 四、结论与分析

1. **WorkStealingThreadPool 综合性能最强**：轻量任务 188 万 TPS、CPU 任务 30.8 万 TPS，均为五种池最高。原因是每个工作线程拥有**独立队列和独立锁**，AddTask 轮询分发把竞争分散到 8 把锁上，工作线程消费自身队列几乎无锁竞争；而其余多线程池共用一把队列锁，且每次 Put 都 `notify_all`，8 个线程惊群抢锁，这是 Fixed/Cache/Scheduled 在 8 核下加速比只有 2.6~2.9× 的根本原因。
2. **FixedThreadPool 稳定可靠**：延迟中位数最低（75μs），常驻线程对突发流量响应即时；适合负载稳定、对延迟敏感的场景。
3. **CacheThreadPool 弹性最好**：实测空闲 60ms 回收线程、流量恢复时约 100~150ms 扩容到满速；适合流量潮汐明显的场景。代价是 sudo 管理线程忙轮询（`yield` 空转）会持续占用约 1 个核，且每波流量初期有爬坡延迟。
4. **SignalThreadPool 语义正确但无并行度**：单线程串行执行，任务严格按提交顺序执行（本报告未直接测顺序，但架构上保证），TPS 约为多线程池的 1/3~1/10，排队延迟随队列深度线性增长（最大 49ms）；适合需要顺序执行、不能并发的任务。
5. **ScheduledThreadPool 定时功能正确**：1 万任务零提前执行，中位误差 0.36ms；但优先队列 O(log n) 操作 + wait_until 多线程共等机制使其普通吞吐偏低（47 万 TPS），高负载下定时误差尾部可达 10~35ms，**适合定时任务，不适合当普通线程池用**。
6. **可靠性**：全部场景 280 万+ 任务零丢失、零拒绝、零崩溃，队列满背压阻塞正确，池销毁均能正常 join 回收线程。

## 五、压测中发现的问题与建议（按优先级）

1. **【惊群】共享队列 `notify_all` 改为 `notify_one`**：[TaskQueue.hpp](include/TaskQueue.hpp) 的 `Add()` 每次入队唤醒全部等待线程，8 线程下每次提交都引发惊群抢锁，是 Fixed/Cache/Scheduled 加速比上不去的主因。生产/消费各唤醒一个即可。
2. **【参数失效】FixedThreadPool / CacheThreadPool 的 `deque_size` 构造参数未生效**：两个池的成员 `m_taskqueue` 是默认构造的（容量固定为 `MaxTaskCount=200`），传入的 `deque_size` 只赋值给了同名成员变量、没有传给队列。建议改为 `m_taskqueue(deque_size)`（Signal/Scheduled/WorkStealing 已正确传递）。
3. **【CPU 空转】Cache/Scheduled 的 sudo 管理线程忙轮询**：`Sudo()` 在队列空时 `yield()` 死循环，空闲时持续吃满一个核。建议改为条件变量等待或 `sleep_for(1ms)` 节流。
4. **【偷取延迟】WorkStealing 空闲线程 50ms 轮询一次**：任务被分到其他线程队列时，空闲线程最坏要 50ms 后才偷到（本次压测持续有负载，未触发；低负载突发时可能出现）。可在 AddTask 后对全局/目标队列做一次 notify 改善。
5. **【日志噪音】停止时打印 `task deque status = false`**：WorkStealing 8 个工作线程退出时各打印一行（本次日志第 14~21 行），属正常停止流程，建议降级为调试日志或删除。
6. **【头文件结构】`WorkStealingThreadPool` 定义在 [ThreadPool.hpp](include/ThreadPool.hpp) 的 `#endif`（第 557 行）之后**：当前因只被一个编译单元包含而能编译，但脱离 include guard 保护，被多个文件包含时会有重定义风险，建议移入 `#endif` 之前。

> 注：本次为单次运行、虚拟机环境的数据，绝对值会随机器负载波动；但五种池的相对差距（WorkStealing ≫ Fixed/Cache/Scheduled ≫ Signal）在多次观察中稳定。复现命令：`cmake --build build && ./bin/test`。
