# 多线程池库（header-only）

一个纯头文件的 **C++17** 线程池实现，一次实现 **5 种调度策略**，配一份完整的**抗压测试报告**（4 个场景、累计 619 万任务、零丢失零崩溃）。

所有类型统一在命名空间 `ctx` 下，只需 include 两个头文件即可使用。

> **2026-09-30 重构**：`CacheThreadPool` 去掉了独立的 `Sudo()` 管理线程，改成「生产者触发扩容 + worker 空闲超时自清理进回收站」。本 README 与 [抗压测试报告.md](抗压测试报告.md)、[线程池设计文档.md](线程池设计文档.md) 的数据均为重构后的实测（2026-10-04）。

## 五种线程池

| 线程池 | 调度策略 | 适合什么场景 |
|---|---|---|
| `FixedThreadPool` | 固定 N 个 worker 常驻，共享一条任务队列 | 负载稳定、对延迟敏感 |
| `CacheThreadPool` | 按需创建线程，空闲 60ms **自行回收**（生产者触发扩容 + worker 自清理进回收站，**没有管理线程**） | 流量潮汐明显的场景 |
| `SignalThreadPool` | 单线程串行执行，严格保序 | 不能并发、要求顺序执行的任务 |
| `ScheduledThreadPool` | 优先队列 + `wait_until`，支持延时任务 | 定时任务 |
| `WorkStealingThreadPool` | 每线程一条**独立队列 + 独立锁**，空闲时去"偷"别人的任务 | 高吞吐、CPU 密集 |

## 关键设计

### 1. 任务队列：两种容器，一个抽象

`Taskdeque` 用 `std::deque` 承载普通任务（FIFO），`PriorityTaskqueue` 用 `std::priority_queue` + 自定义比较器 `CompareTask` 承载定时任务，按到期时间排序。定时池复用前者做就绪队列、后者做延迟队列。

### 2. 队列满时做背压，而不是拒绝任务

队列容量固定为 `MaxTaskCount`（默认 200）。满了以后提交端在 `m_notFull` 条件变量上等待，而不是丢弃或抛异常——**压测中 100 万个任务全部执行完毕、零丢失**，就是这条在兜底。

### 3. Cache 线程池：把管理线程拆掉了（2026-09-30 重构）

最早的 Cache 用一条独立的 **`Sudo()` 管理线程**：它一直活着，轮询队列决定什么时候建线程、什么时候回收。能用，但两个问题绕不开——

- 队列一空它只能 `yield()` **空转，空闲时白白吃掉约一个核**；
- `Stop()` 要 join 它正在管理的线程，而它又在等锁做自清理，**容易绕出死锁**。

重构后把职责**拆回给事件本身**：

| 职责 | 旧（sudo 管理线程） | 新（回收站） |
|---|---|---|
| 扩容 | sudo 轮询队列后 `AddThread()` | **生产者触发**：`AddTask()` 见「有积压且未达上限」直接 `AddThread()`（锁前 + 锁内双重检查防超限） |
| 回收 | worker 把 ID 塞进 `m_exit_threads_id`，sudo 取出来去线程数组里找它、join、erase | worker 超时后**自己**把自己挪进 `m_dead_threads`（回收站）再退出 |
| 统一回收 | sudo 一直活着随时处理 | `Stop()` / 析构时对「在岗组 + 回收站」统一 join |
| 空闲开销 | 一整个核在 `yield()` 死循环 | **0**（没有额外线程） |

`Stop()` 的写法也跟着改：**先在锁内把两组线程对象快照出来，出了锁再 join**。这样正在自清理的线程发现列表已空就直接退出，不会和正在 join 的主线程互相等——这是一处真实的死锁风险。

实测效果：突发场景第 1 波的爬坡从「50ms 只有 10.8 万/s」提到「**50ms 就到 45.9 万/s**」，因为不再需要等管理线程轮询到它（见[抗压测试报告](抗压测试报告.md)场景 4）。

> 注意：**`ScheduledThreadPool` 仍是旧的「sudo 管理线程」实现**（它有 `wait_until` 精确到点的特殊性，当时没一起改），`Sudo()` 里的 `yield()` 空转还在。

### 4. 工作窃取为什么快 2.3~2.9 倍

`WorkStealingThreadPool` 和其余池的根本区别：**每个 worker 一条独立队列、一把独立锁**。

- `AddTask` 用原子计数轮询分发，把竞争分散到 **8 把锁**上
- worker 优先消费自己的本地队列，**几乎无锁竞争**
- 自己队列空了，才去偷相邻线程的（窃取时才触碰对方的锁）

窃取函数 `Stealling_Take` 有三个容易踩坑的细节，代码注释里都写明了：

- **先 `unlock()` 自己的锁，再去 lock 别人的**——否则持自己锁去拿别人的锁，是标准 AB-BA 死锁；
- 偷到任务**直接返回、不塞回自己队列**——塞回去要重新 `lock(m_mutex)`，自己锁自己；
- 都没偷到就 `wait_for(50ms)` 再扫一遍——任务可能被塞进了别人的队列，自己听不到别人队列的 `notify`。

8 核上 CPU 密集任务跑到 **9.3× 加速比**。超过 8 属于超线性，但要诚实说明原因：基准 `SignalThreadPool` 是单线程、却每条任务都要过一把互斥锁，它不是理想的"无锁单线程"基线，所以这个倍数偏高。对比共享队列的 Fixed / Cache，WorkStealing 快 **2.3~2.9 倍**。

### 5. 先建容器，后建线程

线程启动后要互相访问"相邻线程对象"的地址。如果边 `push_back` 边启动线程，`vector` 扩容会让先前传进去的地址全部失效。所以严格分两步：**容器先 `reserve()` 建满、定下最终地址，再创建线程**。

### 6. 头文件自包含

`TaskQueue.hpp` 必须自己 `#include <functional>`（`using Task = std::function<void(void)>` 需要它）。否则一旦它被先于 `<functional>` include，`Task` 未声明会引发一串连锁报错。

## 实测数据

> **测量日期 2026-10-04**（CacheThreadPool 重构后）。环境：Intel i7-14650HX（虚拟机分配 **8 核**）· 3.8 GiB · Ubuntu 20.04 / 内核 5.15 · g++ 9.4.0 · `-O2 -std=c++17 -Wall`
> 配置：worker 上限 8（= `hardware_concurrency`）· 队列容量 200 · Cache/Scheduled 初始 1 线程、空闲 60ms 回收

### 场景 1：轻量任务（100 万空任务，8 生产者并发提交）

| 线程池 | 总耗时 | 吞吐 TPS | 平均延迟 | P50 | P95 | P99 | 最大延迟 | 丢失 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| **WorkStealing** | **0.457s** | **2,187,830** | 131.0μs | 61μs | 469μs | 1,044μs | 9.2ms | **0** |
| Fixed | 1.072s | 932,533 | 113.4μs | 71μs | 331μs | 646μs | 10.5ms | **0** |
| Cache | 1.341s | 745,535 | 185.0μs | 133μs | 479μs | 889μs | 11.6ms | **0** |
| Scheduled | 1.842s | 543,026 | 281.5μs | 226μs | 641μs | 1,156μs | 13.5ms | **0** |
| Signal | 2.765s | 361,638 | 513.5μs | 384μs | 1,363μs | 2,195μs | 15.4ms | **0** |

**100 万任务全部完成、零丢失**；所有池的 drain 时间 ≈ 0，说明消费能跟上提交。Fixed 的平均延迟最低（113μs），WorkStealing 的吞吐最高。

### 场景 2：CPU 密集（20 万任务 × 3000 次 `sqrt`）

| 线程池 | 总耗时 | 吞吐 TPS | 相对单线程加速比 |
|---|---:|---:|---:|
| **WorkStealing** | **0.710s** | **281,866** | **9.3×** |
| Fixed | 2.602s | 76,874 | 2.5× |
| Cache | 2.805s | 71,293 | 2.3× |
| Scheduled | 2.978s | 67,158 | 2.2× |
| Signal | 6.589s | 30,355 | 1.0×（基准） |

### 场景 3：定时精度（`ScheduledThreadPool`，1 万延时任务，延时 50~500ms）

| 指标 | 数值 |
|---|---:|
| 平均误差 | 378.6μs |
| P50 误差 | **291μs** |
| P95 误差 | 899μs |
| P99 误差 | 2,367μs |
| 最大误差 | 7,123μs |
| **提前执行任务数** | **0 / 10000** |

定时语义完全正确：**没有任何任务提前执行**，中位误差不到 0.3ms。尾部误差 P99 2.4ms / Max 7.1ms，比重构前（10.6ms / 34.6ms）**明显收窄**——一是入队/取任务改成 `notify_one` 后不再整队惊群，二是 Cache 池不再有一个核在 `yield()` 空转跟工作线程抢 CPU。

### 场景 4：突发流量与扩缩容（3 波 × 3 万，波间空闲 900ms）

| 时刻 | Cache 累计完成 | 该 50ms 速率 | Fixed 累计完成 | 该 50ms 速率 |
|---:|---:|---:|---:|---:|
| 50ms | 22,979 | 459,560/s | 28,878 | 577,560/s |
| 100ms | **30,000** | 140,420/s | **30,000** | 22,440/s |
| 150~950ms | 30,000 | 0/s（空闲，线程 60ms 超时自行退出） | 30,000 | 0/s |
| 1000ms | 45,185 | 303,700/s | **60,000** | 517,880/s |
| 1050ms | **60,000** | 296,300/s | 60,000 | 0/s |
| 1950ms | 74,326 | 286,520/s | **90,000** | 413,020/s |
| 2000ms | **90,000** | 313,480/s | 90,000 | 0/s |

- **Cache 池扩缩容机制实测有效**：空闲 900ms（> 60ms 超时）后线程确实全部回收，新流量到达后由**生产者直接补线程**，每一波都能在 **50~100ms** 内清空；不再需要等管理线程轮询到它。
- **Fixed** 线程常驻，波峰更高（第 3 波 41.3 万/s vs Cache 31.3 万/s），但两者总耗时几乎一样（Cache 2.902s / Fixed 2.863s，差 1.4%）。
- 结论：Cache 用「空闲时零开销」换来了每波约 2~4 万任务的爬坡损耗，在这个量级下代价可以忽略。

## 压测暴露出的问题

### 已在 09-30 重构中解决

| 问题 | 当时的现象 | 现状 |
|---|---|---|
| **【惊群】** | 共享队列 `Add()` 每次入队 `notify_all`，8 个 worker 同时被唤醒抢一把锁，是共享队列池加速比上不去的主因 | ✅ `TaskQueue.hpp` 生产/消费各改 `notify_one`，只有 `Stop()`（必须唤醒全部）才用 `notify_all` |
| **【参数失效】** | `FixedThreadPool` / `CacheThreadPool` 的 `deque_size` 只赋给了同名成员变量，没传给队列 | ✅ 已改为 `m_taskqueue(deque_size)` |
| **【CPU 空转】**（Cache 部分） | `CacheThreadPool` 的 `Sudo()` 在队列空时 `yield()` 死循环，空闲吃满一个核 | ✅ 管理线程整个拆掉，改为生产者扩容 + worker 自清理（见关键设计第 3 条） |
| **【定时尾部误差】** | P99 10.6ms / Max 34.6ms，惊群放大尾部延迟 | ✅ 复测 P99 2.4ms / Max 7.1ms |

### 仍存在的问题（按优先级）

1. **【机制不一致】** 同一份头文件里，`CacheThreadPool` 已是回收站方案，**`ScheduledThreadPool` 仍是旧的 `Sudo()` 管理线程**——`yield()` 空转吃核的问题在它身上还在。而且 `ScheduledThreadPool::ForceStopThreadGroup()` 是**持着 `b_mutex` 直接 join**，与 Cache 新版「快照后出锁再 join」相反，仍有死锁风险。建议把 Cache 的写法搬过去。
2. **【头文件结构】** `WorkStealingThreadPool` 定义在 `ThreadPool.hpp` 的 `#endif`（第 517 行）之后，脱离 include guard 保护。当前只被一个编译单元包含所以能编译，被多个文件包含时会有重定义风险 → 应移入 `#endif` 之前。
3. **【日志噪音】** `TaskQueue.hpp` 里 9 处 `std::cout << "task deque status = false"`，正常停止流程也会打印（本次压测打印了 8 行）→ 应降级为调试日志或删除。
4. **【偷取延迟】** WorkStealing 空闲线程 `wait_for(50ms)` 才重新扫一遍，低负载突发时最坏要 50ms 才偷到 → 可在 `AddTask` 后对目标队列做一次 notify 改善。
